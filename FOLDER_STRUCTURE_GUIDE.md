# Folder Structure Guide

This guide explains the purpose of the folders in this MERN project. The same separation of concerns can be reused in other full-stack applications; rename or omit sections to fit the project.

## Project root

- `client/` — frontend application. Keeps browser-facing code and its tooling separate from the backend.
- `server/` — backend application. Holds API, data access, and server-side business logic.
- `.git/` — Git's internal version-control data. Git creates and manages this directory; do not store application code here.

## `client/`

- `public/` — static assets served as-is, without being imported and processed by the frontend build system. Use for assets that need a stable public path.
- `src/` — application source code. Keeping app code here makes the boundary between source and project configuration/build output clear.
- `dist/` — generated production build output. Deployment tools serve or package this directory; it is recreated from source and generally should not be edited by hand.
- `node_modules/` — installed frontend dependencies. Package tooling generates this directory from dependency manifests; it is not a place for project code.

### `client/src/`

- `assets/` — images, fonts, and other assets imported by the app and processed with the frontend source.
- `components/` — reusable interface building blocks shared across pages or features.
  - `admin/` — reusable components specific to administrative screens.
  - `common/` — general-purpose components that are not tied to one page or major layout.
  - `layout/` — shared page-frame elements such as headers, navigation, and footers.
  - `routes/` — components that help control or guard route access, such as authentication or role checks.
- `layouts/` — page-level shells that arrange shared interface regions around groups of pages.
- `routes/` — route definitions that map URLs to screens and apply route-level organization or protection.
- `services/` — frontend integrations with APIs and other external services. Centralizing requests keeps network details out of visual components.
- `store/` — shared client-side state and state-management setup for data used across multiple parts of the interface.
- `utils/` — small, reusable helper functions that do not belong to one specific screen or component.
- `views/` — route-level screens, grouped by user-facing feature or area.
  - `admin/` — screens for managing the application.
    - `category/` — administrative screens for category management.
    - `order/` — administrative screens for order management.
    - `product/` — administrative screens for product management.
    - `user/` — administrative screens for user management.
  - `Auth/` — authentication screens and related page-level UI.
  - `Home/` — home or landing screen.
  - `Products/` — product browsing and detail screens.
  - `users/` — user-facing account or profile screens.

## `server/`

- `config/` — server configuration and setup for infrastructure such as databases or application settings. Keep environment-specific values in environment configuration rather than hardcoding secrets.
- `controller/` — request handlers that translate incoming HTTP requests into application actions and responses. Controllers coordinate work rather than owning all business rules.
- `middleware/` — functions that run during the request/response pipeline for cross-cutting concerns such as authentication, validation, and error handling.
- `models/` — data schemas and persistence models. This layer describes how application data is represented and stored.
- `routes/` — API endpoint declarations that connect HTTP methods and URL paths to middleware and controllers.
- `seeds/` — scripts or data sets for initializing or populating a database, commonly for local development or repeatable setup.
- `services/` — business operations and integrations used by controllers. Moving this logic here helps keep request handling and domain behavior separate.
- `tests/` — automated checks for backend behavior. Group tests by feature or test type as the project grows.
- `utils/` — shared backend helpers that are not specific to a single route, model, or service.
- `node_modules/` — installed backend dependencies, generated by package tooling and not a place for application code.

## Reusing this structure

Keep code near the responsibility it serves: screens in views, reusable UI in components, HTTP handling in routes and controllers, domain operations in services, and persistence in models. Add feature-specific subfolders when an area grows, and avoid creating folders that have no clear owner or purpose. Generated folders such as `node_modules/` and build output such as `dist/` are normally recreated by tooling rather than maintained as source.
